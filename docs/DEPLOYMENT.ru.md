# Развёртывание на вашем VPS

Используется ваш Ubuntu VPS. Поставщик сервера не выбирается. База не публикует порт в интернет; приложение доступно через Nginx и HTTPS. Приложение и миграции используют разные роли PostgreSQL. Контейнер API работает без root с файловой системой только для чтения.

## Подготовка

1. Установите Docker Engine и Compose plugin из официального репозитория Docker. Настройте SSH и firewall: снаружи нужны SSH, 80 и 443; PostgreSQL недоступен снаружи.
2. Направьте выбранный DNS-домен API на VPS. Получите действительный TLS-сертификат и разместите `fullchain.pem`, `privkey.pem` в каталоге `TLS_DIRECTORY`. Настройте продление сертификата и `docker compose ... exec nginx nginx -s reload` после продления.
3. Скопируйте `deploy/.env.example` в `deploy/.env`. Права файла — `0600`. Сгенерируйте **разные** случайные hex-строки для двух DB-паролей, JWT_SECRET и RECOVERY_EPOCH, например `openssl rand -hex 32`. Hex не требует URL-кодирования в DATABASE_URL.
4. Укажите домен, абсолютные пути TLS/резервных копий, fingerprint открытого GPG-ключа и адрес своего резервного сервера. Закрытый GPG-ключ храните отдельно от VPS. Для SSH-копирования установите выделенный ключ и проверенный `known_hosts` в BACKUP_SSH_DIRECTORY. Проверка ключа сервера не отключается.

Команды из корня проекта:

```sh
docker compose --env-file deploy/.env -f deploy/compose.yaml build
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d
```

Перед запуском API одноразовый migration-контейнер применяет миграции. Инициализация роли `mrba_app` выполняется только для нового PostgreSQL volume. Для переноса существующей БД DBA должен создать роль и выдать аналогичные гранты отдельно; не удаляйте volume ради повторного init.

Начального владельца создаёт `dist/seed.js`. В защищённом файле `deploy/owner.env` (0600, не в Git) задайте OWNER_LOGIN и OWNER_PASSWORD, затем выполните:

```sh
docker compose --env-file deploy/.env -f deploy/compose.yaml run --rm --env-from-file deploy/owner.env migrate node dist/seed.js
```

Если версия Compose не поддерживает `--env-from-file`, загрузите OWNER_LOGIN/OWNER_PASSWORD в окружение защищённым способом и используйте `run --rm -e OWNER_LOGIN -e OWNER_PASSWORD migrate node dist/seed.js`. DATABASE_URL берётся из конфигурации сервиса миграции. Не передавайте пароль аргументом shell и не сохраняйте его в Git. Seed не заменяет пароль существующего пользователя и не создаёт бизнес-операций. OWNER имеет все функции. Выполните seed после миграций и при добавлении новых permissions.

`EXPO_PUBLIC_API_URL` мобильной release-сборки задаётся как `https://ваш-домен/api/v1`. Release не имеет fallback на локальный сервер. Для распространения на физические iPhone требуются ваш Apple Developer account, signing и TestFlight/выбранный канал распространения. Отладочный симулятор не заменяет эту проверку.

## Контроль запуска

- `GET /api/v1/health/live` проверяет процесс, `health/ready` — соединение с БД.
- Проверьте login, тестовый приход → плавку → отходы → договор → отгрузку на отдельной staging-БД. Не смешивайте тестовые и заводские операции.
- Проверьте Docker health, логи API (requestId, route, HTTP status, duration; без тел запросов и токенов), свободное место, срок TLS-сертификата и свежесть backup.
- Внешний мониторинг должен уведомлять ответственного при недоступности API и просроченном backup. Конкретный канал уведомления предоставляет владелец инфраструктуры.
- Повторно запустите `npm audit`, тесты и проверку восстановления перед выпуском. Проверенные версии фиксируются lockfile и digest развёрнутых образов; обновления сначала проходят staging.

## Резервные копии

Backup запускается при старте контейнера и ежедневно в 22:00 UTC (03:00 Ташкент). `pg_dump -Fc` сначала проходит `pg_restore --list`, затем шифруется GPG, получает SHA-256 и копируется на внешний сервер через SSH. Метка успеха обновляется только после внешней копии. Срок локального хранения — 30 дней по умолчанию. Docker health становится unhealthy, если успешной копии нет более 26 часов. Настройте отдельный контроль доставки и retention на резервном сервере.

Проверка списка архива не заменяет пробное восстановление. Регулярно расшифровывайте выбранную копию на изолированной машине и восстанавливайте в новую БД с `pg_restore --exit-on-error --no-owner`. Сверяйте критические таблицы и остатки с журналом. `node scripts/verify-backup.mjs` автоматически проверяет этот путь для локальной **mrba_test**, не изменяя основную БД.

Это ежедневные логические копии, а не PITR. Потенциальная потеря данных — до интервала между копиями. Если завод требует меньший RPO, перед выпуском нужны согласованные WAL archiving/PITR и тест их восстановления; не обещайте нулевую потерю на ежедневном pg_dump.

## Восстановление после аварии

1. Остановите API, Nginx и задачи backup, чтобы исключить запись во время восстановления.
2. Проверьте SHA-256 зашифрованного файла. Расшифруйте архив закрытым ключом вне публичного VPS или в защищённом временном каталоге.
3. Восстановите в **новую**, пустую БД. Сохраните повреждённую/старую БД до завершения расследования. Проверьте миграции, таблицы, происхождение партий и сверку журнала.
4. Создайте роли и права, примените необходимые миграции. Отзовите все восстановленные refresh-сессии; поменяйте JWT_SECRET и RECOVERY_EPOCH до запуска API. Старые запросы не должны автоматически повторяться после отката БД.
5. Сверьте операции после времени копии с первичными заводскими документами. Не определённые операции в приложении со старым recovery epoch требуют этой сверки; прежние запросы заблокированы намеренно.
6. Протестируйте систему и только затем откройте доступ. Возобновите backup и внешние проверки.

Автоматический откат схемы вниз не предусмотрен. Перед миграцией сделайте проверенную копию; rollback приложения допускается только с совместимой схемой.
